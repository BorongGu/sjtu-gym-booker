# 交大体育场馆预约脚本

自动在开放时刻抢指定场地时段。**设计目标是「不被风控」，不是「最快」。**

## 用法

```bash
node booker.js
```

首次运行会弹出 Edge 窗口，手动完成 jaccount 登录（含双因子）。**之后免登录。**

结束脚本请按 **Ctrl+C**（会顺手把刷新后的会话存下来），别直接叉掉窗口。

### 登录为什么能记住

JSESSIONID 和 jaccount 的都是 **session cookie**，Chromium 关闭即丢 —— 光靠 `.profile/` 目录留不住。
所以脚本额外把 `storageState()` 落盘到 `.state.json`，下次启动注入回去（已实测跨重启有效）。
jaccount 会话过期时会自动重新走一次 SSO，通常无感；只有 jaccount 那边也过期了才需要你再输一次密码。

> `.state.json` 里是**明文**的 JAccount / JSESSIONID 会话，泄漏基本等同账号泄漏。
> 已写进 `.gitignore`，写入时会用 `icacls` 去掉继承、只保留当前用户读写。
> 但它终究是明文文件 —— 别提交、别外传、别丢进同步盘。

需要多套配置时可用环境变量隔离：`SJTU_PROFILE` / `SJTU_STATE`。

## config.json

| 字段 | 说明 |
|---|---|
| `venueId` | 场馆 id，取自预约页 URL 第三段 |
| `motionType` | 运动类型名；留空 = 该场馆第一个 |
| `targetDate` | `"+7"` = 今天+7 天；也可写死 `"2026-09-24"` |
| `slots` | **心仪时段**，按优先级排列；写错格式会直接报错退出 |
| `fallback` | 心仪没抢到时的兜底策略：`nearest`(默认) / `later` / `off` |
| `maxSlotsPerOrder` | 单次最多订几个时段；`0` = 按场馆紧张度自动推定 |
| `fields` | 限定子场地名；`[]` = 任意 |
| `fireAt` | 每日开放时刻，`"now"` = 立即跑一次 |
| `preOpenLeadMs` | 提前多少毫秒开始轻探，默认 1500 |
| `earlyRetryMs` | 日期还没放出来时的重探间隔，默认 150（决定命中开放瞬间的精度） |
| `attemptIntervalMs` | 日期已开放但没抢到时的重试间隔，默认 800 |
| `burstWindowMs` / `burstIntervalMs` | 放号后前 3000ms 用 200ms 短间隔贴住 |
| `attemptIntervalMs` | 突发段结束后的常规间隔，默认 500 |
| `maxAttempts` | 抢位阶段的次数上限，默认 40（探测阶段**不占用**） |
| `probeTimeoutMs` | 只读请求超时，默认 800 |
| `orderTimeoutMs` | 下单超时，默认 12000 |
| `probeWindowMs` / `bookWindowMs` | 两阶段各自的墙钟截止，默认各 20000 |
| `hedgeAfterMs` | 只读请求对冲阈值；`0` = 关闭（默认） |
| `maxErrorStreak` | 连续失败多少次即终止，默认 5 |
| `fallbackImmediate` | 同一份矩阵内心仪为空就立刻兜底，默认 true |
| `dryRun` | **建议先用 true**：只演练到「命中空位」，不下单 |

时段取值必须是整点段：`07:00-08:00` … `21:00-22:00`。写成 `"19:00"`、`"19-20"` 会在启动时报错并列出全部合法值 —— 不会静默跳过。

**先用 `dryRun: true` 跑通。** 首轮会打印真实的「场地 × 时段」可约矩阵，用它核对时段结构对不对：

```
时段          A区  B区
14:00-15:00   ×    ×
15:00-16:00   ×    可约
16:00-17:00   可约 ×
```

## 抢位策略：心仪优先，兜底补位

- **第 1 轮**：只抢 `slots` 里的心仪时段。两个都有位就**一单同时订两个**，只有一个就订一个。
- **第 2 轮起**：心仪仍无位时，从全场剩余席位里按 `fallback` 挑：
  - `nearest`（默认）—— 离心仪时段最近的优先；一样近则**晚的优先**
  - `later` —— 一律越晚越优先
  - `off` —— 只认心仪，绝不将就

### 一次最多能订几个？

不是拍脑袋定的，是逆自前端 `handleChooseSeat` 的互斥逻辑：

| 紧张度 | 前端行为 | 推定上限 |
|---|---|---|
| 正常(0) | 无互斥代码 | 不限 |
| 紧张(1) / 很紧张(2) / 很紧张签退(4) | 已选超过 1 个时踢掉最早选的 | **2** |
| 非常紧张(3) | 已选 1 个时再点会全部清空 | **1** |

脚本启动时会打印实际推定值。想更保守可用 `maxSlotsPerOrder` 手动压低（只能调小，不会突破紧张度上限）。

**这条推定已被官方帮助文本证实**（`/venue/moreSetting/getOne` 的 `help` 字段）：

> 如果场馆状态为"紧张"，则每笔订单只能预订一个场地的 2 个小时，或者 2 个场地各 1 个小时。

同一份文本也证实了另外两项逆向结论：

> 场地更新的时间为每天中午的 12 点。校内人员（使用 Jaccount 账号登录的人员）可预订后 7 天的场地。

即 `fireAt: "12:00:00"` 与 `targetDate: "+7"` 的默认值正确。

## 拥塞与容错

12:00 放号时服务端会明显变慢，以下都是针对那一刻的：

| 问题 | 处理 |
|---|---|
| **站点 axios 默认 `timeout: 50000`** | 只读请求逐个覆盖为 800ms。否则任何一个请求被挂住，整轮就停 50 秒，窗口直接错过 |
| **鉴权失败被误判为「日期未放号」** | 见下方，这是最隐蔽的一条 |
| 探测与抢位共用次数预算 | 拆成两阶段，各自独立次数 + 墙钟截止 |
| 兜底晚一轮才触发 | `fallbackImmediate`：同一份矩阵里心仪为空就立刻兜底，省掉一个 `attemptInterval` |
| 尾延迟 | 只读请求可选对冲（`hedgeAfterMs`），最多 2 个在途；**下单绝不并发** |
| 限流被越捅越深 | 见下方「限流」一节 |

### 限流：实测结论与未解之处

**已确认的事实：**

- 限流响应是 **HTTP 200 + `code: 500` + `msg: "请求过于频繁，请稍后再试"`** —— 不是 429，只能按消息匹配
- 它真实存在且容易触发：多次实测中，连续探测在第 8–9 个请求前后开始被拒

**未能确定的：具体窗口与阈值。** 依次排除了几种假设：

| 假设 | 实测 | 结论 |
|---|---|---|
| 约 4.9 次/秒 | 降到 3.7 次/秒仍被拒 | 不是纯速率 |
| 约 8 个 / 2 秒 | 闸门压到 6 个/2 秒仍被拒 | 窗口比 2 秒长 |
| 对时的 16 连发烧掉了额度 | 与探测间隔 55 秒后仍被拒 | 不是紧邻突发所致 |
| 降到 1.5 次/秒 | 仍被拒 | 短期速率不是主因 |

最可能是**分钟级甚至更长的累计配额**，而连续多轮压测把它耗光了。没有继续试探——
再逼近阈值本身就是封号风险，而这恰恰是本项目要避免的。

**因此采取的策略**是不去贴阈值，而是把足迹压到真正需要的量：

- 对时采样 16→10 次、130→200ms（全脚本最密的一段突发）
- `preOpenLeadMs` 1500→1000，少打无用探测
- `probeRatePerSec: 3`，外加 `reqBudgetPerWindow: 5 / 2s` 全局闸（下单不走闸，保证关键那一枪有额度）
- 识别到限流即退避 `1.5s×n`，连续 3 次终止

真实 12:00 的请求量远小于上述压测：约 2–4 次探测 + 1 次时段查询 + 1 次下单。

> **压测会消耗额度。** 正式抢之前不要反复空跑，尤其别在 12:00 前一小时内。

### 鉴权失败不体现在 HTTP 状态码上

这条值得单独写。实测未登录时业务接口返回的是：

```
HTTP/1.1 200
{"code":401,"msg":"您还未登录或登录超时，请再次登录"}
```

**状态码是 200。** 只看 `status` 会判成成功，接着 `data` 为空又被当成「日期还没放出来」，于是以 150ms 的间隔对着一个已经拒绝你的服务端猛敲 —— 这正是最容易把限流升级成风控的路径。

所以 `classify()` 同时检查三件事：传输层错误、响应体是否为预期 JSON 信封（防 HTML）、`body.code` 是否为 401/403。

### 抢到之后

`code === 0` 即**立刻停止重试**（`done = true; break`），绝不会再发第二单。随后：

1. 终端响一声（`\x07`）—— 12:00 你未必盯着屏幕
2. 复刻前端成功后的跳转：写入 `sessionStorage.newOrderDetailsId`，导航到 `/orderDetails/0`
3. 浏览器窗口置前，付款/详情直接可操作

> 这里有个坑：SPA 的路由守卫查的是 `sessionStorage.token`（按标签页存），**光有 Cookie 会被弹回登录框**。
> 而 jaccount SSO 流程下 `currentUser` 返回的 `data.params` 是空的，拿不到 JSESSIONID，
> 所以退回读 Cookie 里的 JSESSIONID —— 它本来就只是个前端登录标记，真鉴权靠 Cookie。

同样的交接也用在另外两条路径：`1002` 需验证码时跳预约页，下单结果不确定时跳 `/Order` 让你人工核对。

### 下单结果不确定时绝不重试

`ConfirmOrder` 是非幂等写请求。超时、连接断、5xx 时**无法判断订单是否已建**，此时脚本立即停手并提示人工核对「我的订单」，绝不重试 —— 重复下单会带来违约风险。

## 自测

```bash
npm test      # 25 项纯函数断言：上限推定、时段校验、心仪/兜底排序、spaces 构造
npm run verify  # 8 项实时联网验证：webdriver 指纹、超时覆盖、错误分类
```

`npm run verify` 会连真实服务器，确认超时真的生效（不是继承 50s）、未登录响应被正确归类为 `auth` 而非 `ok`。改完网络层逻辑后务必跑一次。

## 开抢时刻怎么定

前端 `get7Days()` 的逻辑：jaccount 用户在 12:00 之前可见未来 7 天，12:00 之后可见 8 天。
也就是**每天 12:00 放出第 8 天的场次**，所以 `fireAt` 默认 `12:00:00`、`targetDate` 默认 `+7`。

### 为什么不掐点开火

`Date` 响应头只有秒级精度。即便用「多样本区间求交」把量化误差压下去，仍对不准到百毫秒级。

最初三轮测到 offset ≈ **-32.8s**、极差 484ms，我当时归因为「后端多机时钟不一致」。
后来把本机 Windows 时钟做了 NTP 校准（原先 `NoSync`，快 32.04s），重测五轮：

```
-436, -372, -356, -239, -115 ms     中位数 -356ms  极差 321ms
```

结论要拆成两半：

- 那 32.8 秒**几乎全是本机漂移**，与服务器无关 —— 说明对时环节本身是必要的，否则会提前半分钟开火
- 校准后仍有 **~320ms** 的残余离散（五轮中还有一轮触发了区间冲突兜底），
  这部分才是服务端侧的真实抖动，量级比我最初说的 0.5~1s 小

所以掐着 `12:00:00.000` 开火依然没有意义 —— 300ms 的不确定性足以让你打空枪。

脚本改成**边沿触发**：提前 `preOpenLeadMs`(1500ms) 开始，每 `earlyRetryMs`(250ms) 用**单个**最轻的请求
探一次「目标日期放出来没有」，一旦出现立刻下单。命中精度只取决于 250ms 的探测间隔，**与时钟误差无关**。

对时仍然做，但只用来决定「什么时候开始探」—— `preOpenLeadMs` 是 1500ms，远大于 320ms 的不确定性，绰绰有余。

> 如果 `npm run verify` 报出的偏移绝对值超过几秒，多半是本机时钟没在同步。
> Windows 上检查：`w32tm /query /status`，若 Type 为 `NoSync` 则需配置时间源后 `w32tm /resync`。

## 请求次数

| 阶段 | XHR |
|---|---|
| 启动·对时 | 16（HEAD 静态图标，不碰业务接口） |
| 启动·其余 | 2（`currentUser`、`queryVenueById`）+ 1 次页面加载 |
| 轻探期·每次 | 1（`queryFieldReserveSituationIsFull`），间隔 150ms，通常几次就命中 |
| 抢位·突发段 | 1/轮，前 3 秒，实测间隔 **251–360ms**（约 11 轮） |
| 抢位·常规段 | 1/轮，实测间隔 **638–789ms** |

峰值出现在突发段，约 **3.7 次/秒，持续 3 秒**；之后降到约 1.4 次/秒。
按默认 `bookWindowMs: 20000` 算，一轮完整运行约 35 次抢位请求 —— 墙钟先于 `maxAttempts: 40` 触顶。
命中即停，撞到「违约/限制/冻结」也立刻停。

> 为什么要突发段：放号瞬间**日期列表和时段矩阵未必同时就绪**。
> 若日期已出现而矩阵还没放位，常规间隔会白白丢掉半秒以上。这是明天实跑要验证的点之一。

> 日期一旦放出，`dateId` 就固定不变，脚本会缓存它，后续重试**直连时段查询**。
> 这样每轮少一次往返（实测 RTT ~80–100ms），同时少发一个请求 —— 速度和请求量上都是净赚。
> 若时段查询失败则清空缓存、下轮重新解析，避免 `dateId` 失效后卡死。

登录环节：停在 jaccount 页面时**零请求**（慢慢做双因子不受影响）；
只有「已跳回本站却仍拿不到会话」才计数，**连续 3 次即退出**并提示手动登录，不会反复重试。

## 为什么这样写（防封号）

| 风险点 | 处理 |
|---|---|
| 请求指纹与真人不符 | 所有请求都在真实 Edge 的页面上下文里，用站点自己的 axios 实例发出；TLS/JA3、请求头顺序、Cookie 全部原生 |
| 加密参数写错被识别 | `sid`/`tim`（RSA）和请求体（AES-ECB）直接调用站点自带的 `Rsa`/`Aes`，**没有手写复现** |
| 抢跑、密集轮询 | 服务器时钟对齐 + 延后触发 + 次数硬上限 + 每次间隔随机抖动 |
| 验证码失败刷屏 | 服务端返回 `1002` 时**立即停手**，打开预约页交由人工完成，不做自动破解 |
| 撞到账号规则还硬试 | 返回含「违约/黑名单/限制/冻结/超出/已达」时立即终止 |

## 最大的封号风险不是技术层面

这套系统有完整的违约记录体系（`/rule/getBreakRule`、申诉接口等）。真正导致停用预约资格的，几乎都是：

1. **抢到了不去、不签到** —— 违约累计直接封预约权限。抢下的场次请务必到场签到。
2. **抢了再退、反复占位** —— 取消行为同样被记录。
3. **同时多处登录 / 多账号代抢** —— 这是最容易被判定为恶意的行为。

脚本能做的只是把「手速」问题解决掉。**只抢自己真会去的场次**，这比任何技术手段都更能保住账号。

## 技术备忘

下单链路（逆自 `pc/static/js/9.*.js`）：

```
POST /manage/venue/queryVenueById                        form   id
POST /manage/fieldDetail/queryFieldReserveSituationIsFull json  {id, feildType, date:今天}  -> 可约日期 + dateId
POST /manage/fieldDetail/queryFieldSituation              json  {fieldType, date, venueId, dateId} -> 场地 x 时段矩阵
POST /venue/personal/ConfirmOrder                         json  headers: sid=RSA(随机16位key), tim=RSA(时间戳)
                                                                body:    AES-ECB-PKCS7(payload, 该key)
```

- 时段矩阵 `priceList[row]`，`status === 0` 才可约。实测各负值含义（前端把三者渲染成同一个 `bought-seat`，不做区分）：

  | status | 含义 | 依据 |
  |---|---|---|
  | `0` | 可约（`count` 字段是剩余名额） | 前端 `handleChooseSeat` 只接受 0 |
  | `-1` | 不在场馆开放时段 | 学生中心 `openTime: 12:00-22:00`，而 `-1` 恰好覆盖 07:00–12:00 这 5 行 |
  | `-2` | 已过期 | 今天 14:33 实测，`-2` 恰好覆盖 07:00–14:00 这 7 行 |
  | `-3` | 开放时段内、已约满 | 实地确认：该健身房放号后几分钟内即被抢空，此后整片变 `-3` |

  > `isAvailable: 0` **不代表场馆停用** —— 约满时它同样是 0，不可据此判断是否开放。
- `queryFieldSituation` 的 `fieldType` 传运动类型 **id**；`ConfirmOrder` 的 `fieldType` 传运动类型 **name**，`venTypeId` 才是 id。
- `spaces` 由格子对象注入 `scheduleTime/subSitename/subSiteId/tensity/venueNum/status` 后，整段 JSON 做 `price` → `venuePrice` 替换。
- 返回码：`0` 成功（data = 订单号）、`1002` 需滑块验证码、`10001` 资料不完整。

### 我们只有客户端，没有服务端源码

以上全部来自逆向 `pc/static/js/*.js` 这些 webpack 产物，服务端是黑盒。从可观测信号能推出栈：
`JSESSIONID` + 302 到 `/login` 是 Java Servlet；`{code,msg,data}` 配 `/system/user/*`、`getPublicKey`、`jsonLogin`
是 **RuoYi（若依）** 脚手架特征；`/captcha/get` + `repCode:"0000"` + `blockPuzzle` 是开源的 **anji-plus captcha**。

实际影响：**前端代码是请求格式的权威规范**（服务端只校验它，所以复刻前端就够）；
但**业务规则**（一次最多几个时段、频次限制、黑名单判定）只能从前端的防御性逻辑反推，
看不到服务端的最终裁决 —— 这就是上面「单次上限」标注为「推定」的原因。
